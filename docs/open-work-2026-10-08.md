English, condensed: the maintainer approved replacing the face macro with an ordinary struct literal inside an
`impl` block — visually the same block, but real syntax, so field names and paths complete natively and a wrong
field is a compile error pointing at the column, with `kind` no longer repeated. Two constraints: the type name
is the `kind` and participates in the identity hash, so renaming the type is a different face; and two readers
must change together — the build-time text reader and the authoring executor that rewrites face files. Landing
order: make the reader accept both forms, switch the snippets and templates, teach the executor the new form,
migrate the existing faces, retire the generated rust-analyzer mirror and its check-cfg line, and only then drop
the old reader. Acceptance is byte-identical identities, products, `graft_plan.tsv`, the ten faces, the rehearsal,
and the executor's own output.

### H 的示例（用 `/tmp/xirang-lab/dash` 里的真文件做底）

**A 新 face 怎么写的示例**（`src/board/card/card.rs`）。**现在**：

```rust
crate::board_object! {
    kind: Card,
    parent: crate::board::NODE_ID,
}
pub struct Card;
```

**候选 A2**（普通 Rust 构造器 ✓ 字段变方法 ⇒ 原生补全 ✓、顺序不再敏感 ✓）：

```rust
/// 卡片：`board` 的子面。
pub const FACE: FaceDeclaration = FaceDeclaration::of(kind::Card)
    .parent(crate::board::NODE_ID);
pub struct Card;
```

带注册机与根面同理：`FaceDeclaration::of(kind::Board).needs_registry(true).registry_rule_path("src/board/registry_rule/registry_rule.rs")` ·
`FaceDeclaration::root(kind::Board)`；外部实现同理：`ExternalObject::of(kind::FrameFast).parent(root_node_id(crate::XIRANG_NAMESPACE))`。
**改动前要先定的两件**：这份常量叫什么（候选 `FACE` / `DECLARATION` / `OBJECT`），以及构建期读者跟着学这一形（它现在的文本读者只认宏块与 `Shape { … }`／`Shape::of(…)`）。

**B `add_crates` 侧的示例**。**现在**（方法名可补全 ✓，`crate::…::SUBTREE` 不行 ✗ —— 这份文件在 crate 图之外）：

**候选 B2**：`crates --write` 在每个生成包内写一份别名模块，把该包认领子树的标记转发出来，声明改成**经包名**引用（编辑器把生成包当普通依赖解析 ⇒ 可补全 ✓）：

**由 `crates --write` 负责的两件**（写者一侧 ✓）：⑴ 在每个生成包里产出 `src/xirang_aliases.rs`，把该包认领子树的 `SUBTREE` 标记 `pub use` 出来 ✓；⑵ 首次切分之后**自动把声明里的 `crate::…::SUBTREE` 改写成经包名的稳定形式** ✓（首次切分之前还没有生成包 ⇒ 那时只能写旧形 ✓，这是 B2 已知的代价 ✓、维护者已接受 ✓）。**两个待定的细节** ✗：**别名怎么命名**（候选：末段大写 `BOARD` ✓ ／整条路径 `BOARD_COLUMN` ✓ ／带前缀 `XIRANG_BOARD` ✓ —— 要定一条**防撞**规则，两棵子树末段同名时必须能区分 ✓）；**改写发生在哪一步**（`--write` 里顺手 ✓ 还是由 `--check` 提示、作者自己贴 ✓）。**验收**：改写法前后，生成树产物 ✓、身份 ✓、`graft_plan.tsv` ✓、十面 ✓、演练 ✓ **逐字不变** ✓；声明文件本身仍必须是**构建期可读的文本** ✓（读者要认新形 ✓）。

**B2 的代价（要一并想清）**：首次切分之前还没有生成包 ⇒ 那时声明只能写 `crate::…::SUBTREE`（不可补全 ✗），`--write` 之后可以**自动改写**成上面的稳定形式；这等于让"声明"与"切分产物"互相引用，值得判一下是否接受。

**✅ 已裁定：C2′ 采用（维护者 2026-10-09「这个可以」）** ✓ —— 计划也做成**普通 Rust 链**：

```rust
pub fn graft_plan() -> Plan {
    Plan::of([
        cut(theirlib::panel::frame).graft(my_graft::frame_fast),           // 单个
        cut(theirlib::panel::gauge).graft(my_graft::gauge_fast),           // 多个 = 数组里多一项
        cut(theirlib::panel::axis).to(theirlib::panel::grid)               // 区间 = .to(…)
            .graft(my_graft::axis_fast),
        cut(theirlib::panel::legend).graft(my_graft::legend_fast).full(),  // 整棵 = .full()
    ])
}
```

**为什么它的补全是"完整"的**（与 B2 不同 ✓）：这份计划**本来就编译在调用 `host!()` 的那个 crate 里** ✓ ⇒ 它是真 Rust ✓ ⇒ 方法名、路径、类型全都能补全 ✓，而 `add_crates` 那份文件在 crate 图之外、只能补到方法名一层 ✓。

**必须逐条保住的语义**（今天的实测与钉子 ✓）：多个＝数组多项 ✓ · 区间＝`.to(…)` 且成员**按注册名顺序各自成一个槽位** ✓ · **`.to(…)` 与 `.full()` 同时用要按名拒绝** ✓（对齐钉子 `full_on_a_range_is_refused_in_both_directions` ✓）· **重叠＝后写的那条赢并主动播报** ✓ · **未被槽位覆盖的子树仍会被剪**（这是既有行为 ✓，不是新引入 ✓）。

**与既有两种拼写的关系** ✗：链形天然是**类型化**的 ✓ ⇒ **字符串拼写仍要保留**给两处：**外部计划数据文件**（`.xirang/external-grafts/<名>/graft.plan` 是**数据**不是 Rust ✓）与旧宏（兼容 ✓）。**因此 A 组第 3 条缺陷（外部计划只认字符串写法 ✗）在 C2′ 之后会变成拦路的那一条** ✓ —— 一处都改成类型化之后，"外部记录对不上类型化切口"就不再是边角情形 ✓。**`FRAMEWORK` 不再重复写** ✓：`Plan::of([...])` 读宿主 crate 根那个常量即可 ✓（今天宏要求它当第一个参数 ✓，我当天就因为漏写撞了 `no rules expected graft` ✗）。

**一个待定细节** ✗：`cut`／`graft`／`to`／`full` 是**自由函数**（`cut(…)` 直接可用 ✓）还是**关联函数**（`Plan::cut(…)` ✓）—— 影响作者要 `use` 什么 ✓。
